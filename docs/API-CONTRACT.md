# Mission API contract

**Status:** Initial framework-neutral mission handlers are implemented on `backend/mission-api-v0.2`; authentication, screening, routing, pricing and database adapters are injected ports. The deployment adapter and live provider integrations remain outstanding.

All routes are versioned under `/v1`. Authentication is required except health checks. The API derives actor ID and role from a verified server-side session; clients cannot submit trusted role or qualification claims.

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| POST | `/v1/missions` | Create a draft from a validated manifest and route endpoints |
| POST | `/v1/missions/{id}/quote` | Calculate and persist a versioned quote |
| POST | `/v1/missions/{id}/publish` | Publish a quoted mission to the dispatch pool |
| GET | `/v1/missions/{id}` | Read an authorized mission projection |
| GET | `/v1/missions/{id}/events` | Read an authorized event timeline |
| GET | `/v1/dispatch/queue` | Dispatcher-only eligible open work |
| POST | `/v1/missions/{id}/assignments` | Dispatcher-only Runner assignment |
| POST | `/v1/missions/{id}/legs` | Create a proposed relay leg plan |
| POST | `/v1/legs/{id}/handover` | Initiate a two-party custody handover |
| POST | `/v1/handovers/{id}/confirm` | Confirm one side of a handover |

## Command headers

Every mutating request must include:

- `Idempotency-Key`: high-entropy client-generated key unique per actor and command scope.
- `If-Match`: expected mission/leg version for optimistic concurrency.
- Authenticated session: actor identity resolved by the API, never accepted from the JSON body.

The API hashes a canonical representation of the request body. Reusing an idempotency key with the same hash replays the original status and body. Reusing it with a different hash returns `409 IDEMPOTENCY_KEY_REUSED`.

## Error envelope

```json
{
  "error": {
    "code": "MISSION_VERSION_CONFLICT",
    "message": "The mission changed. Refresh and retry.",
    "requestId": "opaque-correlation-id"
  }
}
```

Use `400` for malformed input, `401` for unauthenticated requests, `403` for authorization/policy denial, `404` for inaccessible resources, `409` for stale versions or idempotency conflicts, and `422` for validly shaped but policy-ineligible commands. Do not disclose whether another user's private mission exists.

## Atomic command transaction

For each mutation, the API must:

1. Authenticate the request and derive actor/role server-side.
2. Validate schema, scope, idempotency key and expected version. Quote calculation is performed by the trusted pricing service; clients cannot submit or override quote amounts.
3. Begin a database transaction and claim the idempotency receipt.
4. If an identical completed receipt exists, return its original response.
5. Lock the mission/leg and load authoritative Runner qualification and jurisdiction records where required.
6. Execute the pure domain command.
7. Persist the new projection using the expected version, append all emitted events, and store the response receipt.
8. Commit once; otherwise roll back everything.

Assignment must also enforce a database-level uniqueness/locking rule so two dispatch workers cannot assign the same mission concurrently. The first implementation should use PostgreSQL transactions and row locks; a queue or distributed cache can be added when measured load requires it.

## Relay and handover

A relay route is a proposal until each leg is revalidated and accepted. Do not promise a route based on personal flight bookings or unverified traveler availability. A handover challenge is generated by the server, has a short expiry, is bound to the mission, adjacent legs and both actors, and is stored only as a cryptographic hash.
The releasing and receiving parties confirm independently. Only a confirmed handover may move custody to the next leg.

## Implemented API slice

The initial handler currently implements:

- `GET /health` (unauthenticated liveness response)
- `POST /v1/missions` (requester-only draft creation)
- `GET /v1/missions/{id}` (requester, assigned Runner, dispatcher or trust-operator read)
- `POST /v1/missions/{id}/quote` (trusted server-side pricing; client-supplied quote values are rejected)
- `POST /v1/missions/{id}/publish` (requester-only publication)

The handler accepts a verified-principal resolver, manifest screening service, distance estimator, pricing policy provider and mission repository. It does not implement token verification itself: production must connect a maintained identity provider and ensure roles are assigned from trusted server-side claims.
A missing or permissive authentication adapter is not an acceptable deployment configuration.

Manifest screening is a required server dependency. The API sets the domain screening flag only after that dependency approves the submitted terms; a rejected or unavailable screening decision must fail closed. The initial implementation does not yet implement the dispatch queue, assignment, relay-leg or custody endpoints listed above.

## Launch constraints

The API must reject prohibited item classes and hold cross-border/aviation legs until country-specific customs, aviation security, sanctions, insurance and carrier requirements are implemented and reviewed. No medical, organ, blood, pharmaceutical, hazardous or other regulated time-critical transport should be offered by the initial release.
